# UI Surface Map — Hotel Rheinland / Kurort ERP Codebase

**Phase:** Phase 2 Tactical Codebase UI Surface Map  
**Research question:** Which current `repo/` backend modules, tests, and CLI contracts can safely ground Hotel Rheinland staff-facing UI ideas, and where would a UI over-claim because the current repo is CLI-only, stubbed, header-only, or missing a web/API/data contract?

**Method:** Phase 2 used a three-subagent codebase archaeology fan-out, then parent-context file exploration of `repo/README.md`, `repo/src/`, `repo/tests/`, `repo/src/kurort_engine/__main__.py`, `repo/tests/test_f5_receptionist_subcommands.py`, and function/class inventories from named source and test files. This file records exact path/line anchors gathered in this pass. Line anchors are source evidence, not production-readiness guarantees.

## 4. Immediate caveats for later idea artifacts

- **No web/UI/API layer found in this pass.** Evidence points to Python modules, tests, and CLI commands (`repo/README.md:15-16`; `repo/src/kurort_engine/__main__.py:53-64`). Any UI proposal is therefore a design layer over module/CLI contracts, not a discovered existing frontend.
- **Do not re-propose kiosk, self-check-in, guest portal, generic command center, mobile wallet app, compliance cockpit, POS/TSE suite, or housekeeping backend.** Phase 1 duplicate inventory and synthesis already reserve only narrow staff-facing primitives in these areas (`output/findings/phase1_ui_pattern_synthesis.md:11-16`, `:186-192`).
- **Prefer proof labels in UI.** Because many surfaces are test-contract or CLI-contract backed, UI states should label whether an output is generated, previewed, dry-run, stub-shaped, unsupported, or not locally implemented.
