# UI Idea 003 — AVV + Retention Evidence Drawer

**One-line summary:** Add a narrow admin/manager evidence-drawer pattern for AVV processor checks and DSGVO retention cascades, using explicit confirmation copy, proof labels, exception reasons, and audit-hash visibility without re-proposing a broad compliance cockpit or guest self-service cascade.

**Target role / workflow:** Manager, privacy/admin operator, and Kurverwaltung-facing reviewer preparing or reviewing processor suitability evidence, AVV audit packets, retention/deletion previews, and internal audit records.

**Evidence labels:** `module-backed`, `test-contract-backed`, `preview-only`, `stub-shaped`, `requires new API contract`.

## Research question for this artifact

How can Hotel Rheinland staff inspect sensitive AVV/DSGVO evidence and retention impacts safely in the UI while preserving the Phase 1 constraint that broad compliance cockpit and full self-service cascade ideas are duplicate/risky?

## Proposal

Create an **AVV + Retention Evidence Drawer**: a reusable right-side drawer opened from compliance-sensitive rows in the manager/admin interface. The drawer is not a dashboard. It is a microinteraction pattern that shows exactly what evidence exists, what is only previewed, what is stub-shaped, and which sensitive action requires confirmation.

### Drawer variants

| Drawer variant | Trigger | Primary content | Action style | Evidence label |
|---|---|---|---|---|
| AVV processor evidence | Processor row / vendor card | Processor id, AVV status/expiry, cooperation flags, TOM/evidence checklist, suitability result | Review/export proof only | `module-backed`, `test-contract-backed`, `preview-only` |
| AVV audit packet | Audit packet export button | Packet metadata, generated bytes/filename, “stub-shaped packet” warning, reviewer note area | Export with warning | `test-contract-backed`, `stub-shaped` |
| Retention impact preview | Guest retention row / deletion request | Guest id, affected domains, invoice redaction, spa anonymization, channel-manager forget event, Art. 30 audit entry, exception reason | Preview first; require confirmation before run | `module-backed`, `test-contract-backed`, `requires new API contract` |
| Retention run result | Completed cascade event | Run status, retry status, audit hash, affected records summary, manual-review flag | Read-only proof | `test-contract-backed`, `preview-only` |
| Audit event detail | Audit table hash chip | Actor, payload summary, recorded_at, content hash, append order, source module/test proof | Read-only proof | `module-backed`, `test-contract-backed`, `preview-only` |

### Drawer layout

1. **Header proof band:** Shows workflow name, current status, evidence label, and “not a legal certification” warning where applicable.
2. **Evidence checklist:** Lists AVV/TOM/evidence items or retention cascade steps with `present`, `missing`, `stub-shaped`, `manual review`, or `not locally proven` states.
3. **Sensitive-action confirmation panel:** For retention runs and packet export, presents plain-language impact copy and requires the operator to acknowledge unsupported contracts.
4. **Audit proof section:** Shows audit hash / recorded timestamp / append order when available, with copy that avoids WORM/GoBD certification claims.
5. **Open-contract footer:** Lists missing web/API, role-permission, persistence, legal review, final PDF renderer, and reviewer-availability dependencies.

## Confirmation copy and microinteractions

### AVV packet export confirmation

> **Export AVV evidence packet?**  
> This packet reflects the current backend/test contract for processor evidence. The current codebase map flags the packet payload as stub-shaped in at least one source path, so this export must not be presented as final legal documentation until the final PDF renderer, legal review, and signature/hash verification contract exist.

Buttons:

- `Export evidence packet (stub-shaped)` — primary but warning-styled.
- `Cancel` — secondary.
- `Open missing contracts` — tertiary link to footer.

### Retention cascade preview confirmation

> **Preview DSGVO retention cascade before running.**  
> This preview lists the affected guest domains and expected audit entry. It does not prove guest self-service, identity verification, legal-hold review, role authorization, or durable archive storage. Run only after manual review.

Buttons:

- `Run after manual review` — disabled until checkbox is ticked.
- `Keep as preview` — safe default.
- Checkbox: `I reviewed affected domains and unsupported contracts.`

### Audit hash microcopy

> **Audit proof:** This hash/append-order proof is backend-test evidence for the current module. It is not a GoBD-certified WORM archive or multi-user authorization proof.

## Expected impact

- **Safer sensitive actions:** Confirmation copy reduces the risk that a manager runs a retention cascade or exports an AVV packet without seeing impact and unsupported-contract warnings.
- **Clearer compliance evidence:** Evidence drawers give staff and reviewers a single place to inspect processor status, TOM/evidence checklist, cascade steps, exception reasons, and audit hashes.
- **Reduced over-claiming:** `stub-shaped`, `preview-only`, and `requires new API contract` labels make it hard to confuse a backend/test artifact with a final legal PDF, certified archive, or fully authorized workflow.
- **Better implementation slicing:** A Developer can build one drawer variant at a time from existing module/test contracts rather than creating a broad compliance cockpit.

## Effort estimate

**Medium design effort; medium-to-large implementation dependency.**

- Design/prototype effort: **M** — one drawer component with three content templates, warning copy, checklist states, and confirmation variants.
- Backend/API integration effort: **L** until a web/API architecture, role/permission model, durable status store, final PDF renderer, audit storage contract, and legal-review workflow exist.
- Incremental implementation path: **S/M per drawer variant** if built first as read-only proof drawers over existing AVV, retention, or audit outputs.

## Duplication check

This artifact is **not**:

- a broad compliance cockpit;
- a new AVV cascade backend module;
- a new DSGVO Art. 17 self-service cascade;
- a guest portal or identity-verification workflow;
- a legal-hold management system;
- a GoBD/WORM-certified audit archive;
- a final legal PDF renderer or e-signature/signature-verification feature.

It **is** a narrow UI microinteraction layer that makes existing AVV, retention, and audit evidence easier to inspect while clearly labelling preview, stub-shaped, and missing-contract states.

## Open questions

2. What exact packet metadata should be visible for a stub-shaped AVV export: byte length, generated timestamp, processor id, hash, reviewer note, or source test contract?
3. Should retention cascade previews and runs be separate API endpoints, or one endpoint with dry-run / execute modes?

## Minimal acceptance criteria for a future build

- The drawer opens from a specific processor, retention, or audit row rather than from a global cockpit.
- The header always shows an evidence label and unsupported-contract warning where applicable.
- AVV packet export uses `stub-shaped` copy until a final renderer/legal review exists.
- Retention actions are preview-first and require explicit manual-review confirmation before execution.
- Audit proof copy never claims WORM/GoBD/role authorization unless new contracts are added.
- The feature remains staff/admin-facing and avoids guest self-service, broad compliance-cockpit, and new backend-engine scope.
